Shared runner API

run-driver-tests.sh commands

CommandWhat it doesUse when
setup-kind Create kind cluster + install ingress-nginx (ports 80/443) Once per machine / CI job
run <cmd> Deploy operator + ArangoDB + Ingress; export Docker env; run cmd Integration + resiliency

Environment contract · Integration

Runner exports these — drivers only read & forward

You do not set endpoint/auth yourself. Call run-driver-tests.sh run <cmd> with K8S_INGRESS_ADDRESS=127.0.0.1; the runner exports the rest into <cmd>.

Variable (exported by runner)Default / exampleWhat other drivers do
TEST_ENDPOINTS_OVERRIDE http://arangodb.local (default); https://… when Ingress TLS is on Read — use as the driver connection URL (map to ARANGO_URL / etc. if needed)
TEST_AUTHENTICATION_OVERRIDE basic:root:rootpw Read — configure driver auth from this string
TEST_NET_OVERRIDE --net=host --add-host=arangodb.local:127.0.0.1 Forward into docker run (not a driver client setting)
TEST_MODE_K8S k8s Read if your suite branches on k8s mode (optional)
TEST_NOT_WAIT_UNTIL_READY 1 Read if you have non-k8s readiness waits to skip (optional)
K8S_NAMESPACE / K8S_DEPLOYMENT default / arangodb-driver-tests Read — optional for plain integration; required for resiliency kubectl targets

Host must set K8S_INGRESS_ADDRESS=127.0.0.1 for kind. To rename exports: K8S_TEST_ENDPOINTS_ENV=ARANGO_URL (etc.), or map in a thin wrapper.

Environment contract · Resiliency

Extra exports for kubectl chaos (Part A)

Same as integration: runner exports these. Drivers must forward them into Docker so tests can call kubectl.

Variable (exported)What other drivers do
K8S_COORDINATORS_COUNT Read — expect 3 (auto-raised when cmd contains “resiliency”)
K8S_TEST_DOCKER_EXTRA_ARGS Forward into docker run — mounts kubectl + kubeconfig
KUBECTL_BIN / KUBECONFIG_PATH Informational; mounts come from K8S_TEST_DOCKER_EXTRA_ARGS
K8S_NAMESPACE / K8S_DEPLOYMENT Read — pass to chaos helpers as kubectl target

Required Docker pattern

docker run --rm \
  ${TEST_NET_OVERRIDE} \
  ${K8S_TEST_DOCKER_EXTRA_ARGS} \
  -e TEST_ENDPOINTS="${TEST_ENDPOINTS_OVERRIDE}" \
  -e TEST_AUTHENTICATION="${TEST_AUTHENTICATION_OVERRIDE}" \
  -e K8S_NAMESPACE \
  -e K8S_DEPLOYMENT \
  -e K8S_COORDINATORS_COUNT \
  your-test-image \
  <entrypoint>

Without K8S_TEST_DOCKER_EXTRA_ARGS, resiliency tests cannot restart ingress or delete coordinator pods from inside Docker.

Part A · Kubernetes resiliency

Scenarios other drivers must rewrite (#0–#8)

#ScenarioFaultWhat we cover
0LoadBalancerCoordinatorDistributionNone (observe LB)Confirm ingress spreads probes across coordinators (no fault).
1IngressCoordinatorFailoverDelete 1 coordinatorClient recovers after one coordinator pod is killed.
2IngressRestartWhileIdleRestart ingress-nginxSame client works again after ingress restart with no traffic during outage.
3IngressRestartDuringActiveWorkloadRestart ingress-nginxActive requests may fail transiently (A–D); must recover after ingress is back.
4CoordinatorRestartWhileIdleDelete all 3 coordinatorsSame client works after all coordinators are recreated (idle during outage).
5CoordinatorRestartDuringActiveWorkloadDelete all 3 coordinatorsWorkload survives full coordinator restart; any during-fault errors must be A–D only.
6CoordinatorKillDuringReadKill all during cursorStreaming cursor interrupts cleanly; dead-cursor errors (E) allowed on resume/close.
7CoordinatorKillDuringInsertKill 1 during insertsInsert loop may see A–D (or none); inserts succeed again after recovery.
8CoordinatorKillDuringCursorIterationKill all after ~30 docsDeeper cursor stream interrupts cleanly; same interrupt + dead-cursor checks as #6.

Accept error categories A–E, not exact strings. Run HTTP/1 and HTTP/2 where Go does. Idle scenarios (#2, #4) expect no during-fault errors; #5/#7 may see zero failures. Full steps/asserts: deploy/kubernetes/documentation/driver-resiliency-reference.md.

Language-agnostic assertions

Error categories A–F (accept by category)

A — Connection lost

refused, reset, EOF, broken pipe

Accept during fault

B — Timeout

deadline exceeded, I/O timeout

Accept during fault

C — Gateway JSON

HTTP 502/503/504 + JSON body

Accept during fault

D — Non-JSON gateway

502/503/504 + non-JSON body / Content-Type (e.g. HTML)

Accept during fault

E — Cursor gone

404 / 409 / 410 JSON on cursor APIs

Cursor scenarios

F — Application

401, validation, normal not-found

Never during fault

HTTP/1 and HTTP/2 often return different text for the same fault — classify, do not assert one exact message.

Environment contract · Toxiproxy

run-toxiproxy — runner defaults vs driver work

Driver→ 127.0.0.1:17001→ Toxiproxy→ Ingress→ Coordinator

Runner exports all rows below. Other drivers do not invent listen/admin ports — they read them, start test/toxiproxy.sh, and point the client + admin helpers at those values.

Variable (exported by runner)DefaultWhat other drivers must do
TEST_ENDPOINTS_OVERRIDE http://127.0.0.1:17001 Read — connect the driver here (not to arangodb.local)
TEST_INGRESS_HOST arangodb.local Read if TLS/Host header needed; usually optional on plain HTTP
TOXIPROXY_UPSTREAM ingress IP:80 or :443 Pass through to toxiproxy.sh start (do not hardcode)
TOXIPROXY_LISTEN_PORT / TOXIPROXY_ADMIN_PORT 17001 / 8474 Pass through to toxiproxy.sh; listen = data, admin = toxics
TEST_TOXIPROXY_ADMIN http://127.0.0.1:8474 Read in tests — AddToxic / Disable / Enable via admin API
TEST_TOXIPROXY_PROXY arangodb Read in tests — proxy name for admin calls
TEST_NET_OVERRIDE same as integration Forward into docker run

Drivers must also set TESTCONTAINER=<name> when calling toxiproxy.sh (required by the script). Host still sets K8S_INGRESS_ADDRESS=127.0.0.1.

Part B · Network faults

Toxiproxy scenarios to port (#1–#14)

1–3 Connection cut

reset_peer, disable proxy, connection reset → category A

4–6 Latency

High / extreme / remove latency → succeed or B

7–8 Timeouts

Client context + server header timeout → B (#8 HTTP/1 only)

9–10 Packet loss

Partial reset mix; full timeout toxic → A / B

11–12 Streaming

Disconnect during cursor / query start → A

13–14 Writes

Insert / commit disconnect — outcome unknown → A

Reuse test/toxiproxy.sh for container lifecycle. Each language implements admin API helpers (AddToxic, Disable, …) and error classifiers.

Adoption pattern

Example wrapper for any driver

#!/usr/bin/env bash
# scripts/run-k8s-tests.sh — map shared env → driver-native names
export ARANGO_URL="${TEST_ENDPOINTS_OVERRIDE}"
export ARANGO_AUTH="${TEST_AUTHENTICATION_OVERRIDE}"

docker run --rm \
  ${TEST_NET_OVERRIDE} \
  ${K8S_TEST_DOCKER_EXTRA_ARGS:-} \
  -e ARANGO_URL -e ARANGO_AUTH \
  -e K8S_NAMESPACE -e K8S_DEPLOYMENT -e K8S_COORDINATORS_COUNT \
  -e TEST_TOXIPROXY_ADMIN -e TEST_TOXIPROXY_PROXY \
  your-driver-test-image \
  <npm test | pytest | mvn verify>

# Invoke via shared runner:
# K8S_INGRESS_ADDRESS=127.0.0.1 \
#   bash ./deploy/kubernetes/run-driver-tests.sh run bash scripts/run-k8s-tests.sh

arangojs

Map to TEST_ARANGODB_URL; prefer Dockerized mocha for k8s suites.

Java

Keep Maven; replace starter cluster with runner for k8s lanes; align toxics with Part B.

Python

Map to --host/--port or env; run pytest inside Docker on kind.

Per-driver checklist

What each driver team should do

Bring shared pieces

  • Copy deploy/kubernetes/run-driver-tests.sh (+ README)
  • Copy test/toxiproxy.sh
  • Follow driver-resiliency-reference.md
  • CircleCI: install kind + kubectl; call setup-kind

Implement language pieces

  • Wrapper that honors exported env + Docker flags
  • Integration tests against Ingress endpoint
  • Resiliency helpers: kubectl delete pod, ingress restart
  • Toxiproxy admin client + category A/B asserts
  • Rewrite scenarios #0–#8 and #1–#14

Existing starter-based CI can stay for day-to-day unit/integration; add separate k8s jobs for the shared lanes (as Go already does).

Takeaway

Same cluster. Same faults. Same categories. Language-specific assertions only.

Start from deploy/kubernetes/README.md, implement the env contract, then port Part A and Part B from deploy/kubernetes/documentation/driver-resiliency-reference.md (authoritative steps, budgets, and observed errors — complete reference for other drivers).
